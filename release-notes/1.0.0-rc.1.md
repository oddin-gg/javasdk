# Java SDK 1.0.0-rc.1

The first release candidate of the Java SDK 1.0, a rewrite of the SDK with the same public API. It is for testing: please run it against the integration environment and tell us what you find. The final 1.0.0 follows after the candidates have been through the test environment.

## What changes for you

- **New coordinates, no registry.** The SDK is published to Maven Central as `gg.oddin.oddsfeed:odds-feed`, no GitHub Packages token needed. 0.0.x was `com.oddin.oddsfeed:odds-feed`.
- **Java 25.** 0.0.x was Java 8 and Kotlin. 1.0 is plain Java; no Kotlin and no RxJava on your class path. Java 8 clients stay on the 0.0.x line, which gets critical fixes until 31 March 2027.
- **Source compatible, not binary compatible.** Code that compiles against 0.0.x compiles against 1.0 with the exceptions below. Recompile; a library of yours compiled against 0.0.x and used with 1.0 can fail with `NoSuchMethodError`. Packages and class names are unchanged.
- **Same behaviour unless it was a bug or the design needed it.** Every deliberate behaviour change is listed below.
- **Signed.** The jar and the POM on Maven Central carry GPG signatures (the `.asc` files), and the GitHub release has the jar, the POM and their signatures attached.

```xml
<dependency>
  <groupId>gg.oddin.oddsfeed</groupId>
  <artifactId>odds-feed</artifactId>
  <version>1.0.0-rc.1</version>
</dependency>
```

Remove the old dependency when you add the new one: both jars have the same packages. Documentation: [integration guide](https://github.com/oddin-gg/javasdk/blob/main/docs/integration-guide.md), [configuration](https://github.com/oddin-gg/javasdk/blob/main/docs/configuration.md), [health and logging](https://github.com/oddin-gg/javasdk/blob/main/docs/health-and-logging.md), [FAQ](https://github.com/oddin-gg/javasdk/blob/main/docs/faq.md). Small runnable [examples](https://github.com/oddin-gg/javasdk/tree/main/examples/odds-feed-1.0): start, resume after a restart, event recovery and replay.

## What is new

- **Backpressure.** A message is acknowledged after your callback returns, with a prefetch of 200 per session (`setAmqpPrefetch`, 1 to 10 000). A slow listener slows its own queue on the broker, not your heap. Bodies over 1 MiB (`setMaxMessageSize`) are not decoded and are reported as unparsable.
- **No client code on SDK threads.** Message callbacks run on a thread of their own session, `oddsfeed-session-<id>`; global callbacks run on one events thread. Heartbeats, recovery and timers can never be blocked by your code.
- **No blocking in caches, no deadlocks, bounded REST.** Four permit pools, one deadline per call (`setHttpClientTimeout`, 30 s), retries with backoff inside it, a REST concurrency limit (`setRestConcurrencyLimit`, 16), parallel loads instead of one by one.
- **Health.** `OddsFeed.getHealth()` returns the feed's state, a state per part (`HealthComponent`: consumer, sessions, alives, recovery, events, timers, threads, catalogs, connection and API) and typed counters (`counters()` has stable names for a metrics exporter); `onHealthEvent` tells each change. A watchdog finds stalled callbacks and queues, deadlocks among the SDK's threads and a recovery thread that has died (the `RECOVERY` part is stalled at its next look, with the reason, and the feed can no longer recover: close it and open a new one). An access token the API refuses (HTTP 401 or 403) makes the `API` part stalled until a call succeeds, besides `onFatalError`. A channel the broker keeps refusing degrades the connection part. Thresholds: `setCatalogStaleLimit`, `setCallbackStallLimit`, `setQueueStallLimit`, `setWatchdogInterval`, `setConnectionDownLimit`.
- **A safety net for a feed far behind.** When live messages stay older than `setStaleMessageLimit` (2 min) for `setStaleMessageWindow` (1 min), the SDK asks for a recovery and replaces the session's channel, at most three times per ten minutes; then the session is marked lagging.
- **Recovery you can see.** `RecoveryManager.getEventRecoveryStatus(requestId)` (pending, completed, failed, timed out), `onProducerCauseChange` with a `ProducerStatusCause`, `ProducerManager.getProducerStatus`, `getActiveProducersInScope`, `onSafetyNetEvent`, `onSessionLagChange`. Resuming after a restart: save `Producer.getTimestampForRecovery()` and pass it to `setProducerRecoveryFromTimestamp` before `open()`. The resume point and a recovery's start never pass the producer's own now: a message stamped more than a second ahead of its producer's clock moves no recovery mark. A recovery that starts later than where its gap began, because the producer's stateful recovery window is shorter, is logged with how much of the gap is dropped.
- **More events on the global listener**, all `default` methods, so a 0.0.x listener compiles as it is: `onConnectionStateChange` (up as well as down), `onFatalError`, `onCallbackFailure`, `onApiCall`.
- **More configuration**: `setStartupTimeout`, `setShutdownTimeout`, `setMaxInactivitySeconds`, `setMaxRecoveryExecutionMinutes` (360 at least), `setExchangeName`, `setReplayExchangeName`, `setApiCallLogging`, `setDefaultLocale`, `setPreloadLocales`, `setEagerEntityPreload`, `setMessagingSslContext`.
- **Single-item getters and clears**: `SportsInfoManager.getSport`, `getTournament`, `getPlayer` without a locale, `clearPlayer`, `clearSport`; `MarketDescriptionManager.reloadMarketVoidReasons`; `ReplayManager.getReplayStatus`.
- **Tournament and sport details, as in the Go SDK**: `Tournament.getIconPath()` (from the tournament's info, the same in every locale), `Tournament.getCompetitorIds()` and `Sport.getTournamentIds()`, read from what the SDK already holds, without loading the competitors or building the tournaments. All three are `default` methods, so an implementation of your own still compiles.
- **Raw data as bytes**: `OddsFeedExtListener.onRawFeedMessageBytes` and `onRawApiDataBytes`. The generated XML classes keep the number as decoded next to each enum getter (`getStatusRaw()`), and an unknown enum value decodes to `UNKNOWN`.
- **Telemetry**: `User-Agent` `oddin-javasdk/<version> (java <version>)` and `X-Oddin-SDK-Version` on every API call, `SDK_version` in the broker connection's properties, `OddsFeed.getSdkVersion()`.
- **Logging**: SLF4J only, quiet at INFO (state changes), throttled warnings; the access token is redacted from what the SDK logs, from its exception messages and from what the broker quotes. `setApiCallLogging(true)` logs every API call attempt at INFO under its own logger, `com.oddin.oddsfeedsdk.api-calls`, so it can go to a file of its own (see [health and logging](https://github.com/oddin-gg/javasdk/blob/main/docs/health-and-logging.md#the-api-call-log)).
- **XML parsing**: feed messages and API responses are parsed with DTDs and external entities off.

Not in 1.0: `Category`, reference ids, `Statistics` on the match status and a settlement's void reason id and parameters. The Go SDK decodes them, but the feed and the API do not send them, so they are not planned. A bet cancel's void reason id and parameters are sent, and 1.0 reads them as 0.0.x does.

## Also coming in this candidate

- **A correct status or score update is no longer held back by a message stamped in the producer's future.** A status or score stamped ahead of its producer's clock (a component with a fast clock, say) used to hold back the following updates of that match until the producer's clock passed it: they were delivered, but wrote nothing (KD-13). Now a timely live message received after it takes over when their receipts and stamps differ by more than a margin, and it never goes below the last update before the bad stamp. Two new settings: `setFutureStampMargin` (default 30 s, at most a day) and `setTimelyMessageAge` (default 10 s, at most half the margin; `build()` refuses a larger value). A message that answers a recovery request never takes over.
- **A message's age is right after a step of the wall clock.** The age that decides whether a message older than the match status age (20 minutes) writes the match status could be wrong by the size of the step until the producer's next alive measured the clock offset again: a fresh message looked old after a step forward and was not written, and an old one looked fresh after a step back. The age is now read with the producer's offset as of the message's own reading. No API change.

## Differences from 0.0.x

### Compile-time differences (the public API)

The complete list is `odds-feed/src/test/resources/api/differences.txt`; a test fails when the API differs from 0.0.59 in a way it does not list.

1. **Kotlin extras are gone.** `data class` `copy()` and `componentN()` no longer exist, and Kotlin callers lose named arguments for these Java methods: pass them by position.
2. **`MarketMessage.getMarkets()` returns `List<? extends Market>`.** Code that assigns it to `List<Market>` needs one cast.
3. **Getters for attributes the feed never sends are deprecated and return null:** `Market.getRefId`, `Outcome.getRefId`, `OddsChange.getBetStopReason`, `getBetStopReasonData`, `getBettingStatus`, `getBettingStatusData`, `BetSettlement.getCertainty`, `BetCancel.getSupercededBy`, `FixtureChange.getNextLiveTime`, `getStartTime` (it returned 1 January 1970, KD-4), `OutcomeSettlement.getDeadHeatFactor`, `OutcomeOdds.getAdditionalProbabilities`, `CompetitorOutcomeOdds.getHomeOrAwayTeam` and `getTeam`.
4. **Internal types moved.** Gone from the public API: `ProducerData`, `EntityFactory`, `MarketData`, `MarketDataFactory`, `MarketDescriptionFactory`, `MarketFactory`, `ChannelConsumer`, `ExchangeNameProvider`, `FeedMessageFactory`, `MarketInitializer`; every `*Impl` class, the caches, `ApiClient`, the dependency-injection types and the managers' internals are in `internal` packages. Code that imported them stops compiling; they were never meant to be used.
5. **Jakarta XML Binding.** The XML schema classes carry `jakarta.xml.bind` annotations instead of `javax.xml.bind`. Code that builds its own `JAXBContext` over them must use Jakarta too.
6. **Sessions are built before `open()`.** After it, `build()` and `buildReplay()` throw `IllegalStateException` (KD-29).
7. **Constructors and factories added for Kotlin callers' sake** (the companion functions `EventStatus.fromApiEventStatus`, `fromFeedEventStatus`, `LiveOddsAvailability.fromApiEvent`, `MarketStatus.fromFeedValue`, `FixtureChangeType.fromFeedType`, and `ApiException` constructors without the defaulted arguments).
8. **The schema classes** (`OF*` for the feed, `RA*` for the REST API) are generated from the schema instead of written by hand. They keep their names, packages and getters, so code that casts the payload of `onRawFeedMessageReceived` or `onRawApiDataReceived` keeps working, with these exceptions:
   - *Feed classes, gone because the feed never sends them:* reference ids and extended specifiers (`getRefId`, `getRefEventId`, `getEventRefId`, `getExtendedSpecifiers`), `getSupercededBy`, `getCertainty`, `getDeadHeatFactor`, `getBetstopReason`, `getBettingStatus`, `getCashoutStatus`, `getMarketMetadata`, the outcome probabilities and `getTeam` of `OFOddsChangeMarket.OFOutcome`, `getNextLiveTime` and `getStartTime` of `OFFixtureChange`, `getResults` of `OFSportEventStatus`, the settlement market's `getResult` and `getVoidReason*`, and the types `OFMarketMetadata`, `OFResultType`, `OFResultsType`, `OFStatisticsScoreType`. `OFEventStatus` values `SUSPENDED`, `ENDED`, `DELAYED`, `INTERRUPTED`, `POSTPONED`, `ABANDONED` and `OFChangeType.FORMAT` are deprecated.
   - *Shape changes:* `OFPeriodScoreType` home and away score are primitives; `OFSportEventStatus`'s scoreboard-available is a `Boolean` (`isScoreboardAvailable()` stays, `getScoreboardAvailable()` tells a missing value from false); the rollback messages' market classes are nested in their message (`OFRollbackBetCancel.OFRollbackBetCancelMarket`, `OFRollbackBetSettlement.OFRollbackBetSettlementMarket`) and their `getMarket()` lists them.
   - *Feed classes, added:* `UNKNOWN` on `OFChangeType`, `OFEventStatus`, `OFFavourite`, `OFMarketStatus`, `OFOutcomeActive`, `OFResult`; raw getters (`getStatusRaw`, `getResultRaw`, `getMarketStatusRaw`, `getChangeTypeRaw`, `getActiveRaw`, `getFavouriteRaw`, `getSpecifiersRaw`) and setters; `getRequestId` on the two rollback messages; `getWinnerId` on `OFSportEventStatus`.
   - *REST classes, gone because the API never sends them:* reference ids on sports, sport events, teams, tournaments, market and outcome descriptions; `getGeneratedAt` on the competitor profile; `RADelayedInfo`, `getDelayedInfo`, `getNextLiveTime` and start-time-confirmed on `RAFixture`; `getMatchStatus` and `getPeriod` on `RASportEventStatus`.
   - *REST classes, reshaped by the schema:* `RAError`'s action and message are text, so `RAErrorAction` and `RAErrorMessage` are gone; `RAPeriodScoreBase` and `RASportEventStatusBase` are merged into `RAPeriodScore` and `RASportEventStatus`; `RAPlayerProfileEndpoint.Player` is the shared `RAPlayer`, and `RACompetitorProfileEndpoint.getPlayers()` lists `RAPlayer`; the sports list is `RASportExtended` (it carries the icon path), so `RASport.getIconPath` is gone; `ObjectFactory`'s methods return `jakarta.xml.bind.JAXBElement`.
   - *REST classes, added:* `RAPlayer`, `RAFixtureCompetitors`, `RASportExtended`, `RAReplayStatusEndpoint`, aggregate scores, winner and `getStatusCode` on `RASportEventStatus`, raw getters for the values as sent, and setters the generated classes have for every attribute.
   - Both raw callbacks get a `default` method that delivers the raw XML bytes.
   - The schema is vendored. A shape change of a public class is never taken within the 1.x line; additive schema changes are.

### Behaviour differences

These are found by running the same system tests against 0.0.59 and 1.0, or by reading both sources. Each entry names its number in `system-tests/KNOWN-DIFFERENCES.md`, which has the details, the reason and the test. (KD-8 and KD-10 were withdrawn: they are no difference.)

**Starting and closing**

- KD-36: the feed's start needs the API. It fetches whoami and the producer list, trying again for the startup timeout, 90 s by default (`setStartupTimeout`), then throws `InitException`. 0.0.x failed within seconds when only whoami was down and fetched the producer list later. A readiness check that failed fast during an API outage waits up to 90 s now.
- KD-44: `setInitialSnapshotRecoveryInterval` refuses a negative interval with `IllegalArgumentException` and keeps the value it had (0.0.x took it and asked from a time in the future). Zero still asks from now, with no history, as in 0.0.x.
- KD-34: `open()` is one-shot. After one that failed, close the feed and build a new one; 0.0.x let the same feed try again.
- KD-29: a session built after `open()` is refused instead of silently receiving nothing.
- KD-15: closing a feed whose start failed logs nothing; 0.0.x logged an error.
- KD-16: a login the broker refuses surfaces as the SDK's `InitException`, with the broker's reason and the token left out, instead of the AMQP client's own exception.
- KD-19: the broker's certificate and host name are checked against the JVM's trust, as 0.0.59 does (0.0.58 and older trusted any certificate). A client with a truststore of its own, or behind a TLS-inspecting proxy, passes an `SSLContext` to `setMessagingSslContext`, which 0.0.59 does not have; on 0.0.59 the proxy's CA goes into the JVM's trust.
- KD-23: closing the feed is no longer reported as `onConnectionDown`.
- KD-30: an event recovery asked for before `open()` returns null and sends nothing (0.0.x sent it, and what it recovered reached no queue). After `open()` a request is also refused while the connection is down or with 128 in flight.
- KD-31: raw API data reaches the extended listener from the feed's first start, before `open()` too. It is delivered on the events thread, after the getter returned, and can be dropped past 1 000 queued entries or 32 MiB.
- KD-32: a recovery-from timestamp set before `open()` is kept (0.0.x lost it); one set after `open()` is ignored with a warning (0.0.x took it until the first up). A producer disabled before `open()` stays disabled.

**Delivery and threads**

- KD-41.1: message callbacks run on the session's own daemon thread, not the AMQP client's consumer thread; a `ThreadLocal`, MDC or thread name your callback relied on sees another thread.
- KD-35: every global callback runs in order on one events thread, from a control queue and a telemetry queue. Producer status, cause, session lag, health, connection state and fatal errors have one slot each: behind a slow callback you hear the newest state, not every step. Recovery completions and safety-net events are each delivered.
- KD-9: a callback that throws is reported to `onCallbackFailure` (flagged as client code), not as an unparsable message. A failure of the SDK's own after decoding goes there too, flagged as the SDK's, and reaches no session callback.
- KD-41.3: a body over `setMaxMessageSize` (1 MiB) is not decoded, has no raw callback, and is reported to `onUnparsableMessage` and `onCallbackFailure`.
- KD-38: `getLastProcessedMessageGenTimestamp` and `getProcessingQueDelay` follow your sessions only, not the SDK's own alive channel; with a session stuck, the delay keeps growing.
- KD-42: a message stamped 0 or less does not move the last processed timestamp.

**Producers and recovery**

- KD-7: the alive check runs from the start, every second: a producer silent longer than the maximum inactivity (20 s) is down with `ALIVE_INTERVAL_VIOLATION`, never-up ones included; 0.0.x waited a minute. A producer processed late during its first recovery stays down until on time.
- KD-1: `onEventRecoveryCompleted` is called (0.0.x never called it, apart from one producer scope configuration).
- KD-37: a recovery completes when every session that takes the producer and snapshot completions has seen its `snapshot_complete`; 0.0.x completed on the first. A producer may come up later.
- KD-28: `Producer.getTimestampForRecovery()` is the resume point the sessions have processed; 0.0.x reported the last alive, which can run ahead and lose messages when persisted. It is not clamped to the stateful window: `setProducerRecoveryFromTimestamp` throws `IllegalArgumentException` for a point too old, then pass 0. Resuming can repeat messages.
- KD-33: a recovery after a producer gap starts from the newest subscribed alive (capped at the producer's now), not the last one received.
- KD-11: a recovery request the API refused is asked for again with backoff, three times, then after a cool-down; on 0.0.58 and later every five minutes, on 0.0.57 and older after the maximum recovery time.
- KD-25: a recovery whose `snapshot_complete` never arrives is given up after five minutes and asked for again with backoff (0.0.58 and later: five minutes too, checked only at an alive and asked again at once). `setMaxRecoveryExecutionMinutes`, 360 at least, bounds the rest.
- KD-26: one recovery in flight per producer. An unsubscribed alive after the API accepted it means the producer lost it: it is given up and the next alive asks again, rather than at once per alive. An unsubscribed alive counts as an alive.
- KD-12: after a reconnect the producer goes down, a recovery starts where each session had got to, and the producer comes back up (0.0.x did not recover what was sent while the connection was down). KD-27: a channel the broker closes on a live connection is opened again; 0.0.x left the session receiving nothing.
- KD-43: durations between two local events (a producer's inactivity, the deadlines and backoffs of a recovery, the safety net's windows, how long an event recovery's status is kept) run on the monotonic clock. A step of the wall clock forward by more than the maximum inactivity, or a virtual machine that resumes, took every producer down with `ALIVE_INTERVAL_VIOLATION` in 0.0.x and asks for recoveries; it takes none down in 1.0. What is published stays wall time. A message's age is read with the producer's offset as of the message's own reading, so a step of the wall clock does not show in it. 
- KD-17: the stale-message safety net (new, see above) is on by default.
- KD-2: as 0.0.x: an alive saying a down producer is unsubscribed raises no `onProducerStatusChange`; the new `onProducerCauseChange` hears it.
- KD-3: a message from a producer the list does not have is dropped, and `getProducer` returns null (0.0.x made up a producer).
- KD-18: a producer listed as `live|prematch` has both scopes (0.0.x left it none).
- KD-41.4-7: the interests are checked before any producer is disabled; a feed whose only session is `SYSTEM_ALIVE_ONLY` asks for no recoveries and tells no producer up; a stateful recovery window of 0 is not clamped; `RecoveryInfo.getSuccessful()` is false for a recovery given up.

**Messages and entities**

- KD-6: bet stop groups separated by a pipe are split (0.0.x did not). KD-5: a bet cancel's `getVoidReason()` returns the void reason (0.0.x: always null).
- KD-13: an older message does not overwrite the status of a newer one; KD-14: a message older than 20 minutes does not write the match status as current. Both are still delivered. The order is the message's own stamp; 0.0.x wrote every one. A status or score stamped in the producer's future no longer holds the correct updates after it back for long: a timely message received after it takes over (see the live-state change above). KD-21: the feed's `winner_id` is used (0.0.x dropped it). KD-39: a field a message leaves out keeps its value (period scores, scoreboard availability, status code).
- KD-20: home and away are the competitors qualified `home` and `away`, for any format but a race, where 0.0.x took the first and second competitor of a "classic" match only. A race, or a match without both, has neither (null under either strategy).
- KD-24: American odds are the moneyline odds: 2.5 reads 150, where 0.0.x gave -97.5. Odds of 1 or less, or not finite, read null.
- KD-22: a getter of several locales fails as a whole when one fails; 0.0.x answered from the others.
- KD-40: a tournament with no competitors has an empty list (0.0.x threw or returned null).
- KD-41.2: REST: one deadline per call, up to three attempts, 16 entity calls at once. A burst of cold getters can fail "waiting for its turn" where 0.0.x was only slow; recovery requests are retried after a 5xx with the same request id.
- KD-41.8-16: maps per locale are copies; `getActiveTournaments(sport, locale)` is in the locale; available tournaments and the sport list are cached for 24 hours; catalogs refresh an hour after the fetch, and a market missing from a list refetches it, whenever the list held is a minute old (a market new upstream can read no name for up to a minute plus the fetch; markets that are never there cost one fetch a minute at most); a response leaves a field it omits as it is; a TV channel without `stream_url` has an empty URL; a competitor without players is not loaded again for each `getPlayers()`; `getMatchStatus()` describes in the match's locales; `getFixtureChanges` reads a time without a zone as UTC and leaves a bad id out.

## Where 0.0.59 already behaves like 1.0

The system tests run unchanged against 0.0.59 and 1.0, so these are known:

- **Delivery**: at most once; gaps are closed by recovery. Multi-session with priority interests and the interest validation, the default exception strategy (`THROW`) with the same results getter by getter, the cache ages (matches, fixtures, tournaments 12 h; competitors, players 24 h; live status 20 min), the cache size defaults, the 20 s maximum inactivity and 360-minute maximum recovery time, lazy start, `close()` at any time and more than once, the fixture-change de-duplication (producer, event id and change timestamp, one hour, so a replay run again within the hour has its fixture changes dropped on both lines), recovery messages reaching every matching session, recovery methods returning the request id as a `Long`, and `FIRST_RECOVERY_COMPLETED` once per producer.
- **0.0.59**, a security release of the 0.0.x line with no API change: the broker's certificate and host name are checked (KD-19), XML is parsed with DTDs and external entities off, and the access token is kept out of the SDK's log lines, exception messages and a channel's description. Every 0.0.x client should be on it.
- **0.0.58 and later**: a lost `snapshot_complete` is given up after five minutes (KD-25: 1.0 adds backoff and a finer rule); a refused recovery is asked for again after five minutes (KD-11); player `underage` and the competitor's underage status.
- **0.0.56 and later**: side-loads off the message thread, no cache lock held across an API call, an observer that throws no longer switches off its cache: the fixes for the message loss that the 0.0.49 to 0.0.54 releases had. 1.0 builds the same guarantees into its design, enforced by tests.

## Fixes from the Go and .NET SDKs

Swept to 2026-10-19 (Go SDK 1.4.0 to `d626983`, .NET SDK 2026-09-07 to `66fcfca`; nothing after 4 October needed porting):

- A channel the broker takes on a live connection is opened again and the session told, so recovery covers what the old queue held (Go, KD-27).
- A recovery whose `snapshot_complete` never arrives is given up after five minutes (Go, KD-25), and a recovery request the API refused is asked for again with backoff, not at every alive (Go, KD-11).
- A tournament's icon path, the ids of a tournament's competitors and of a sport's tournaments (Go).
- The generated XML models match the schema; golden tests decode every vendored fixture strictly (Go).
- A sport's tournament list is replaced as a whole by each response, one write, in the API's order, and one bad id no longer drops the rest (.NET).
- No cache lock is held across an API call, and a failing side-load no longer switches off its cache (.NET; in 0.0.56 and later too).
- A known `underage` is not reset by a payload without it (Go and .NET).

## Known limits of this candidate

- With the API down, each call that needs the feed's start waits up to the startup timeout (KD-36).
- Nothing remembers a failed entity load, as in 0.0.x and the Go SDK: during an API outage each cold getter waits its deadline again. Concurrent reads of the same entity share one request, and every call is bounded by one deadline (`setHttpClientTimeout`).
- The name of a cold dynamic market variant (the players of a player-props market, say) is one request on the thread that reads it, as in 0.0.x. Preload the locales you read and keep name reads off the session's thread if a restart with many variants must be quick.
- Binary compatibility is not promised.
