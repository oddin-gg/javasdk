# Java SDK 1.0.0-rc.2

The second release candidate of the Java SDK 1.0. It fixes two defects found by a long run of 1.0.0-rc.1 against the test environment; nothing else changes. Everything in the [1.0.0-rc.1 notes](https://github.com/oddin-gg/javasdk/blob/main/release-notes/1.0.0-rc.1.md) still applies.

```xml
<dependency>
  <groupId>gg.oddin.oddsfeed</groupId>
  <artifactId>odds-feed</artifactId>
  <version>1.0.0-rc.2</version>
</dependency>
```

## Fixes

- **A closed feed is released.** In rc.1 every `OddsFeed` that was closed stayed in memory for the life of the JVM, with its caches: the JDK's HTTP client keeps an HTTP/2 connection's idle timeout after it is shut down, and that held the SDK's response handler, which held the feed. An application that closes a feed and opens a new one grew its heap with each feed it closed. A test now makes a call over HTTP/2, closes the client and checks that it is collected.
- **No event reaches the listener once `close()` has begun.** In rc.1 an API call answered or cut off while the feed closed could still be reported to `onApiCall` after `close()` had begun, and an event already queued could be delivered. `close()` now stops the events dispatcher first, so nothing of the feed's reaches the global listener once it has begun, as documented. A listener may still call `close()` from its own callback.

## Clarified

- **A lagging session and its producers.** When the safety net's resets are spent and a session lags (`onSessionLagChange`), the net itself takes no producer down. A producer that the session processes later than the maximum inactivity (`setMaxInactivitySeconds`, 20 s by default) is down for that processing delay, as in 0.0.x, with `PROCESSING_QUEUE_DELAY_VIOLATION`, and comes back with `RETURNED_FROM_INACTIVITY` once the session is on time again. This is how rc.1 behaved; the documentation of `SessionLagChange` said otherwise and is corrected.
